# DineOS 顾客端检查与打包功能

检查日期：2026-10-06。依据当前本地代码、隔离界面测试及 PostgreSQL 查询测试；不是线上全部流程已经通过的声明。

## 本次已完成：堂食 / 打包

- 购物车提供 **Dine in / Take away（堂食 / 打包）**，默认堂食。
- 类型属于每张订单。同一桌可先下堂食，再下另一张打包订单；一张订单里的所有餐点使用同一种类型。暂不支持同一张订单中部分餐点打包。
- 顾客订单列表、详情、追踪、桌账单显示类型。打包完成提示到柜台取餐，不再提示送到桌上。
- 厨房显示醒目的 TAKE AWAY / 全部打包提示；打包订单 ready 后操作名称为 Mark collected。
- 员工首页新增打包队列，可看到桌号、订单、餐点、备注、配料以及是否可取餐。
- 管理员订单列表可按堂食 / 打包筛选，详情和最近订单显示标记。
- 柜台代客下单也可选择类型，付款明细及订单管理显示标记。
- 已付款收据保存每张订单的类型。混合结账显示 Dine in / Take away，并在打包餐点下标注 TAKE AWAY。
- 字段保存到 Supabase orders.order_type，由服务端验证，只接受 dine_in / take_away。旧客户端省略类型时默认堂食；旧订单保留，金额不变。
- 不增加包装费、不改变服务费/SST规则、不添加在线付款、不增加无桌号外带流程。
- 数据库 migration 023 已应用，本地 API 已重启。**本次没有推送 Git、没有部署 Netlify 或 Render。**

### 建议你实际测试

1. 扫 Table 1 QR，以访客进入，选餐点，在购物车选择 Take away 后下单。
2. Kitchen 应显示打包标记、餐点备注及配料，准备好后显示 Ready for collection。
3. Staff 首页应看到对应打包订单；Admin 筛选 Take away 应找得到。
4. 再下一张 Dine in，确认同桌两种订单不会混淆。
5. 按现有流程把打包订单标为已取餐、堂食订单标为已送餐，再由柜台付款；查看收据上的混合类型和打包餐点标记。
6. 重印仍应显示类型；旧收据视为堂食；收费保持原有规则。

目前收款仍沿用现有条件：订单达到 served（打包显示为 Collected）才进入待付款列表。这次没有把外带改成先付款后取餐。若餐厅要先收款，需要另外明确更改付款流程，不能只修改按钮文字。

## 已有的必要功能，不必重复新增

访客下单、会员注册/登录、菜单搜索/分类、售罄处理、数量限制、特殊备注、可选配料和必选项、过敏/食材资料展示、服务费/SST/总额、订单追踪、订单详情、再次下单、准备前取消、呼叫员工、请求账单、积分和奖励。服务端重新校验菜单、收费、有效会话，使用幂等键减少重复订单；已付订单不会直接删除。

## 优先修复：有代码依据的实际问题（本次仅检查，尚未修改）

### 1. 网络失败会误判为退桌【高】

CustomerSessionProvider 每 30 秒验证会话，但 catch 将任何失败都当作桌会话结束，直接 setSession(null)。API 暂时离线、500 或网络超时都可能把顾客踢出，会员及订单页面随之无法访问。

建议区分真实失效与临时错误：服务端明确确认凭证无效/会话结束才清理；临时错误保留当前桌并提示重连。顾客请求层也需要保留 HTTP 状态和错误码。

依据：src/context/CustomerSessionProvider.jsx 的 verify/catch；src/services/customerApi.js 的 request。

### 2. 刷新后购物车和当前桌信息没有恢复【高】

CartProvider 只使用内存 state；CustomerSessionProvider 的 readStoredSession 返回 null，saveSession 是空函数。刷新会丢失未提交的餐点及当前桌入口。数据库里的订单仍在，不等于浏览器能自动恢复它们。

建议设计“恢复当前桌”流程，校验数据库中的同一次用餐，不创建新的独立访客会话。草稿恢复也要有桌/用餐边界、过期处理与菜单重新校验，避免上一桌或上一轮用餐的餐点残留。你之前指定使用数据库共享桌，不能未经确认改回各浏览器独立顾客 session。

依据：src/context/CartProvider.jsx；src/context/CustomerSessionProvider.jsx。

### 3. 付款后订单追踪页过早清掉会话【高】

Tracking 在最新订单 served + paid 时调用 clearSession，没有检查同桌/同顾客是否还有未付款订单。即使柜台尚未清桌，也可能失去查看历史或继续点餐的入口。

建议付款只更新账单和订单状态，历史仍保留；以柜台清桌、服务端会话完成为真正结束信号。

依据：src/pages/customer/Tracking.jsx 的 useEffect。

### 4. 分单账单选项与后端信息不一致【高】

Bill 发送 billMode / requestedAmount，但 public/service-requests 只保存 note，员工收到的记录没有保留这两个选择。页面却表示员工会按选择准备账单。另外访客共享同一个桌会话时，“只付自己的餐点”没有可靠的个人订单归属；默认选 Split bill 可能误导。

建议共享访客默认整桌账单，隐藏或解释按个人分单的限制。需要分单时由柜台选择餐点/订单。请求账单的范围和金额应由服务端根据实际未付订单计算，不能信任顾客提交的金额；员工页面显示范围和当时请求状态。

Bill 还固定显示 Payment pending，即使该 participant 已付款、余额为零。应使用实际 paymentStatus，并避免无未付订单时继续请求结账。

依据：src/pages/customer/Bill.jsx；server/src/index.js 的 POST /api/v1/public/service-requests。

### 5. 会员登录验证太弱【真实商用前重要】

目前顾客会员登录用 Member ID + 电话号码匹配，不是验证手机持有权；知道这两个资料的人可能关联别人的会员并使用其积分。

建议至少引入真正的身份验证（例如验证过的账号或一次性验证码）、尝试次数限制和可恢复的登录方式。员工 Supabase Auth 不代表顾客会员也已采用相同验证。

依据：server/src/index.js 的 POST /api/v1/public/members/login。

### 6. 取消订单仍可能显示接单进度【中】

Tracking 对 cancelled 找不到步骤时把 statusIndex 设为 0，仍显示 Received 和预计时间。历史列表虽可显示取消，追踪页也应有明确的已取消终态，隐藏等待进度和取餐提示。

取消确认文案还写“订单未到厨房”，但 received 已经在厨房列表里。准确说法应是“厨房尚未开始准备”。

依据：src/pages/customer/Tracking.jsx；src/pages/customer/OrderHistory.jsx 的确认提示。

### 7. 下单期间菜单涨价缺少明确确认【中】

购物车定期读取菜单、服务端也按当前价重新计算，是正确的。但菜单价格/配料价格在最后一次读取与提交之间变化时，顾客总额没有与服务端确认总额绑定。店铺收费 revision guard 不能覆盖菜单本身的价格变化。

建议提交预期价格版本或预期总额，服务端不一致返回“价格已变化，请确认”，展示差额，再由顾客确认，而不是默默用新价格下单。

依据：src/pages/customer/Cart.jsx；server/src/index.js 的 insertPreparedOrder。

### 8. 请求超时、失败重试入口不足【中】

公共 API fetch 没有明确超时，网络卡住时可能长时间停在 Placing order / Sending request。部分错误页只能等待定时轮询或手动刷新，未提供可操作的 Retry。

建议合理超时、保留幂等键、先确认是否已成功下单再重试；显示“无法确认结果，请查看订单”而不是一律“下单失败”。错误页加重试按钮，失败不清空购物车。恢复会话与请求结果也要覆盖刷新场景。

依据：src/services/customerApi.js；src/hooks/useMenu.js、useCustomerOrders.js、useTableSummary.js；相关 StatePanel。

## 小细节与后续优化

- 共享桌访客可输入 Name，但 Cart 实际不更新共享桌姓名。应隐藏/解释此输入，或者正式保存订单级取餐姓名。打包尤其需要明确叫号或取餐名字。
- 清空购物车目前直接执行；有餐点时建议二次确认或短时间 Undo，避免误触。
- 购物车只有数量/移除，没有直接编辑备注/配料入口；建议允许编辑该行，而不必删除后重新选。
- 呼叫员工成功后只有 toast，顾客看不到 pending / completed 历史；建议显示“请求已收到/处理中/完成”，减少重复按。
- More 对访客只显示 Call staff，进入点餐后不容易再找到“加入会员”。可加不影响当前桌与购物车的会员入口。
- 如过敏资料为空，当前完全隐藏。资料缺失不应被误解为“没有过敏原”；可提示有疑问请询问员工，实际信息需店家维护。
- 顾客打包后如何确认已经领取：当前是厨房操作 Mark collected。实际使用可考虑让前台员工确认取餐，且服务端限制 ready→served、版本校验与审计，避免准备好就误算已取走。
- 预计时间当前主要依据数量/状态，不是实时厨房排队负载。可先明确“预计”；更精确队列估算是后续优化，不需要先做承诺倒计时。
- 默认勾选 Email notifications；建议用户主动选择，并解释通知用途，只有实际实现发送时才展示对应承诺。
- 无桌号外带、外卖、在线付款、储值钱包、多店不是目前必须补齐的功能。先保证下单、送餐/取餐、付款、历史与断网恢复可靠。

## 建议实施顺序

1. 网络错误不退桌 + 付款不提前退出。
2. 恢复当前桌/草稿，并保持数据库共享桌方案。
3. 修正账单模式、请求传递和已付款显示。
4. 取消终态、失败重试、改价确认。
5. 会员验证与会员入口，再做其他操作小细节。
